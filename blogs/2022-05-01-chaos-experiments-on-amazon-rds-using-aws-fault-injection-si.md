<p>Performing controlled chaos experiments on your <a href="https://aws.amazon.com/rds/">Amazon Relational Database Service (RDS)</a> database instances and validating the application behavior is essential to making sure that your application stack is resilient. How does the application behave when there is a database failover? Will the connection pooling solution or tools being used gracefully connect after a database failover is successful? Will there be a cascading failure if the database node gets rebooted for a few seconds? These are some of the fundamental questions that you should consider when evaluating the resiliency of your database stack. Chaos engineering is a way to effectively answer these questions.</p> 
<p>Traditionally, database failure conditions, such as a failover or a node reboot, are often triggered using a script or 3rd party tools. However, at scale, these external dependencies often become a bottleneck and are hard to maintain and manage. Scripts and 3rd party tools can fail when called, whereas a web service is highly available. The scripts and 3rd party tools also tend to require elevated permissions to work, which is a management overhead and insecure from a least privilege access model perspective. This is where <a href="https://aws.amazon.com/fis/">AWS Fault Injection Simulator (FIS)</a> comes to the rescue.</p> 
<p>AWS Fault Injection Simulator (AWS FIS) is a fully managed service for running fault injection experiments on AWS that makes it easier to improve an application’s performance, observability, and resiliency. Fault injection experiments are used in chaos engineering, which is the practice of stressing an application in testing or production environments by creating disruptive events, such as a sudden increase in CPU or memory consumption, database failover and observing how the system responds, and implementing improvements.</p> 
<p>We can define the key phases of chaos engineering as identifying the steady state of the workload, defining a hypothesis, running the experiment, verifying the experiment results and making necessary improvements based on the experiment results. These phases will confirm that you are injecting failures in a controlled environment through well-planned experiments in order to build confidence in the workloads and tools we are using to withstand turbulent conditions.</p>

<h4>Example—</h4> 
<ul> 
 <li>Baseline: we have a managed database with a replica and automatic failover enabled.</li> 
 <li>Hypothesis: failure of a single database instance / replica may slow down a few requests but will not adversely affect our application.</li> 
 <li>Run experiment: trigger a DB failover.</li> 
 <li>Verify: confirm/dis-confirm the hypothesis by looking at KPIs for the application (e.g., via CloudWatch metric/alarm).</li> 
</ul> 
<h3>Methodology and Walkthrough</h3> 
<p>Let’s look at how you can configure AWS FIS to perform failure conditions for your RDS database instances. For this walkthrough, we’ll look at injecting a cluster failover for<a href="https://aws.amazon.com/rds/aurora/features/"> Amazon Aurora PostgreSQL</a>. You can leverage an existing Aurora PostgreSQL cluster or you can launch a new cluster by following the steps in the Create an <a href="https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/CHAP_GettingStartedAurora.CreatingConnecting.AuroraPostgreSQL.html">Aurora PostgreSQL DB Cluster</a> documentation.</p> 
<p><strong>Step 1: Select the Aurora Cluster.</strong></p> 
<p>The Aurora PostgreSQL instance that we’ll use for this walkthrough is provisioned in us-east-1 (N. Virginia), and it’s a cluster with two instances. There is one writer instance and another reader instance (Aurora replica). The cluster is named chaostest, the writer instance is named chaostest-instance-1, and the reader is named chaostest-intance-1-us-east-1a.</p> 
<p><img alt="Under RDS Databases Section, the cluster named chaostest is selected. Under the cluster there are two instances which is available. Chaostest-instance-1 is the writer instance and chaostest-instance-1-us-east-1a is the reader instance. " class="aligncenter wp-image-12036 size-full" height="726" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image12-Original-Copy-1.png" width="2152" /></p> 
<p>The goal is to simulate a failover for this Aurora PostgreSQL cluster so that the existing chaostest-intance-1-us-east-1a reader instance will switch roles and then be promoted as the writer, and the existing chaostest-instance-1 will become the reader.</p> 
<p><strong>Step 2: Navigate to the AWS FIS console.</strong></p> 
<p>We will now navigate to the AWS FIS <a href="https://us-east-1.console.aws.amazon.com/fis/home?region=us-east-1#Home">console</a> to create an experiment template. Select Create experiment template.</p> 
<p><img alt="Under FIS console, Create experiment template needs to be selected." class="aligncenter wp-image-11982 size-full" height="916" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image2-Original.png" width="2718" /></p> 
<p><strong>Step 3: Complete the AWS FIS template pre-requisites.</strong></p> 
<p>Enter a Description, Name, and select the AWS<a href="https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles.html"> IAM Role</a> for the experiment template.</p> 
<p><img alt="Under create experiment template section, Simulate Database Failover is entered for the Description field. DBFailover is entered for the Name field(Optional). FISWorkshopServiceRole is selected for the IAM role drop down field. " class="aligncenter wp-image-11983" height="329" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image3-Original-1024x612.png" width="550" /></p> 
<p>The IAM role selected above was pre-created. To use AWS FIS, you must <a href="https://docs.aws.amazon.com/fis/latest/userguide/getting-started-iam-service-role.html">create an IAM role</a> that grants AWS FIS the permissions required so that the service can run experiments on your behalf. The role follows the least privileged model and includes permissions to act on your database clusters like trigger a failover. AWS FIS only uses the permissions that have been delegated explicitly for the role. To learn more about how to create an IAM role with the required permissions for AWS FIS, refer to the <a href="https://docs.aws.amazon.com/fis/latest/userguide/getting-started-iam-service-role.html">FIS documentation.</a></p> 
<p><strong>Step 4: Navigate to the Actions, Target, Stop Condition section of the template.</strong></p> 
<p>The next key section of AWS FIS is Action, Target, and Stop Condition.</p> 
<p><img alt="Action, Target and Stop Conditions section is highlighted in the image. " class="aligncenter wp-image-11984" height="375" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image4-Original-1024x698.png" width="550" /></p> 
<p><strong>Action</strong>—An action is an activity that AWS FIS performs on an AWS resource during an experiment. AWS FIS provides a set of pre-configured actions based on the AWS resource type. Each Action runs for a specified duration during an experiment, or until you stop the experiment. An action can run sequentially or in parallel.</p> 
<p>For our experiment, the Action will be aws:rds:failover-db-cluster.</p> 
<p><strong>Target</strong>—A target is one or more AWS resources on which AWS FIS performs an action during an experiment. You can choose specific resources or select a group of resources based on specific criteria, such as tags or state.</p> 
<p>For our experiment, the target will be the chaostest Aurora PostgreSQL cluster.</p> 
<p><strong>Stop Condition</strong>—AWS FIS provides the controls and guardrails that you need to run experiments safely on your AWS workloads. A stop condition is a mechanism to stop an experiment if it reaches a threshold that you define as an Amazon CloudWatch alarm. If a <a href="https://docs.aws.amazon.com/fis/latest/userguide/stop-conditions.html">stop condition</a> is triggered while the experiment is running, then AWS FIS stops the experiment.</p> 
<p>For our experiment, we won’t be defining a stop condition. This is because this simple experiment contains only one action. Stop conditions are especially useful for experiments with a series of actions, to prevent them from continuing if something goes wrong.</p> 
<p><strong>Step 5: Configure Action.</strong></p> 
<p>Now, let’s configure the Action and Target for our experiment template. Under the Actions section, we will select Add action to get the New action window.</p> 
<p><img alt="The action section displays Name,Description, Action Type and Start After fields. There is a Add action button that needs to be selected. " class="aligncenter wp-image-11985" height="315" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image5-Original-1024x586.png" width="550" /></p> 
<p>Enter a Name, a Description, and select Action type aws:rds:failover-db-cluster. Start after is an optional setting. This setting allows you to specify an action that should precede the one we are currently configuring.</p> 
<p><img alt="Under Actions section, DBFailover is entered for the Name field. DB Failover Action is entered for the Description field. aws:rds:failover-db-cluster is entered for the Action Type field. Start after field is left blank and Clusters-Target-1 is selected for the Target field. The save button will save the info entered for the respective fields. " class="aligncenter wp-image-11986" height="390" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image6-Original-1024x725.png" width="550" /></p> 
<p><strong>Step 6: Configure Target.</strong></p> 
<p>Note that a Target has been automatically created with the name Clusters-Target-1. Select Save to save the action.</p> 
<p>Next, you will edit the Clusters-Target-1 target to select the target, i.e., the Aurora PostgreSQL cluster.</p> 
<p><img alt="Under Targets section, the edit button for Clusters-Target-1 is highlighted. " class="aligncenter wp-image-11987" height="198" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image7-Original-Copy-1024x338.png" width="600" /></p> 
<p>Select Target method as Resource IDs, and select the chaostest cluster. &nbsp;If you are interested to select a group of resources, then select Resource tags, filters and parameters option.</p> 
<p><img alt="Under Edit Target section, Clusters-Target-1 is selected for the Name field. aws:rds:cluster is selected for the Resource type field. Action is set as DBFailover. Resource IDs is selected for the Target Method field. Chaostest cluster is selected for the Resource IDs drop down box. Save button is also available in this section to save the configuration. " class="aligncenter wp-image-11989" height="450" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image8-Original-911x1024.png" width="400" /></p> 
<p><strong>Step 7: Create the experiment template to complete this stage.</strong></p> 
<p>We will wrap up the process by selecting the create experiment template.</p> 
<p><img alt="Create experiment template option is highlighted. The user will click this button to proceed creating a template. " class="aligncenter wp-image-11990" height="217" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image9-Original-1024x371.png" width="600" /></p> 
<p>We will get a warning stating that a stop condition isn’t defined. We’ll enter create in the provided field to create the template.</p> 
<p><img alt="After selecting the create experiment template option in the previous screen, the user is prompted to enter &quot;create&quot; in the field to proceed. " class="aligncenter wp-image-11991" height="229" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image10-Original-1024x585.png" width="400" /></p> 
<p>We will get a success message if the entries are correct and the template will be successfully created.</p> 
<p><img alt="&quot;You successfully created experiment template&quot; success message is displayed in the screen and its highlighted in green color. " class="aligncenter wp-image-11992" height="391" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image11-Original-1024x501.png" width="800" /></p> 
<p><strong>Step 8: Verify the Aurora Cluster.</strong></p> 
<p>Before we run the experiment, let’s double-check the chaostest Aurora Cluster to confirm which instance is the writer and which is the reader.</p> 
<p><img alt="Under the RDS section, chaos cluster is listed. The user is confirming that chaostest-instance-1 is the writer and chaostest-instance-1-us-east-1a is the reader. " class="aligncenter wp-image-11994" height="236" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image12-Original-1024x345.png" width="700" /></p> 
<p>We confirmed that chaostest-instance-1 is the writer and chaostest-instance-1-us-east-1a is the reader.</p> 
<p><strong>Step 9: Run the AWS FIS experiment.</strong></p> 
<p>Now we’ll run the FIS experiment. Select Actions, and then select Start for the experiment template.</p> 
<p><img alt="Under the experiment template section, the Simulate Database Failover template is selection. Under the actions section, option Start is selected to start the experiment. The other options under Actions section includes Update, Manage tags and Delete. " class="aligncenter wp-image-11996" height="258" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image13-Original-1024x480.png" width="550" /></p> 
<p>Select Start experiment and you’ll get another warning to confirm if you really want to start this experiment. Confirm by entering start say Start experiment.</p> 
<p><img alt="Under the Start Experiement section, user is promoted to enter &quot;start&quot; in the field to start the experiement. " class="aligncenter wp-image-11998" height="221" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image14-Original-1024x565.png" width="400" /></p> 
<p><strong>Step 10: Observe the various stages of the experiment.</strong></p> 
<p>The experiment will be in initiating, running and will eventually be in completed states.</p> 
<p><img alt="The experiment is in initiating state. " class="aligncenter wp-image-11999" height="341" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/28/Image15-Original-Copy-1024x437.png" width="800" /></p> 
<p><img alt="The experiment is in Complete state." class="aligncenter wp-image-12051" height="397" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/29/Image16-Original-Copy-1-1024x508.png" width="800" /></p> 
<p><strong>Step 11: Verify the Aurora Cluster to confirm failover.</strong></p> 
<p>Now let’s look at the chaostest Aurora PostgreSQL cluster to check the state. Note that a failover was indeed triggered by FIS and chaostest-instance-1-us-east-1a is the newly promoted writer and chaostest-instance-1 is the reader now.</p> 
<p><img alt="Under RDS Section, Chaostest cluster is shown. This time, the writer is chaostest-instance-1-us-east-1a." class="aligncenter wp-image-11994" height="270" src="https://d2908q01vomqb2.cloudfront.net/7719a1c782a1ba91c031a682a0a2f8658209adbf/2022/04/29/Image17-Original-1.png" width="800" /></p> 
<p><strong>Step 12: Verify the Aurora Cluster logs.</strong></p> 
<p>We can also confirm the failover action by looking at the Logs and events section of the Aurora Cluster.</p> 
<p><img alt="Under the Recent Events section of the chaos-test cluster, the failover messages is displayed. <h3>Clean up</h3> 
<p>If you created a new Aurora PostgreSQL cluster for this walkthrough, then you can terminate the cluster to optimize the costs by following the steps in the <a href="https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/USER_DeleteCluster.html">Deleting an Aurora DB cluster</a> documentation.</p> 
<p>You can also delete the AWS FIS experiment template by following the steps in the <a href="https://docs.aws.amazon.com/fis/latest/userguide/working-with-templates.html">Delete an experiment template</a> documentation.</p>
